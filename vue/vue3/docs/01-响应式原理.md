# 01 · 响应式原理：数据变化时，函数为什么会自动重新执行

> 对应源码：`src/reactivity/`。可视化演示：`examples/reactivity.html`。
> 参考书目：《Vue.js 设计与实现》第 4～7 章。
>
> 建议先记住一句话：**读取时记录"谁读了我"（track），写入时通知"读过的人"（trigger）。**
> Proxy 只是拦截读写的手段，effect 是"被通知的人"，scheduler 决定"什么时候通知"。

## 一、全景图

```
                    ┌──────────────────────────────┐
                    │  targetMap (WeakMap 账本)     │
                    │  原始对象 → Map{ 属性 → Set } │
                    └──────────────────────────────┘
                        ▲ track            │ trigger
        读属性时记录     │                  │  写属性时通知
   effect(() => {       │                  │
     state.count        │                  │  state.count++
   })                   │                  │
        ┌───────────────┴──────────────────┴──────────┐
        │              ReactiveEffect                  │
        │  run() 重新执行；scheduler 决定何时执行        │
        └─────────────────────────────────────────────┘
```

四个文件、四件事：

| 文件 | 职责 | 一句话 |
|---|---|---|
| `dep.js` | track / trigger + 账本 | 记录"谁读了我"，通知"读过的人" |
| `effect.js` | ReactiveEffect | 把一个函数变成"能被响应式驱动的函数" |
| `reactive.js` | Proxy handlers | 拦截读写，在正确的时机调用 track/trigger |
| `ref.js` / `computed.js` | 原始值与派生值 | 复用同一套 track/trigger 的两种包装 |
| `scheduler.js` | 批量更新队列 | 多次数据变化合并成一次执行 |

## 二、effect：驱动器（effect.js）

```js
const runner = effect(() => console.log(state.count))
// 立即执行一次 → 执行过程中读到的响应式属性全部记到这个 effect 头上
// 之后任何被记下的属性变化 → effect 自动重新执行
```

三个关键实现细节：

**① activeEffect 与栈**。effect 可以嵌套（组件渲染里渲染子组件），
用一个栈保证内层跑完能恢复外层的"当前 effect"。

**② 执行前清理旧依赖（cleanupEffect）**。effect 重新 run 之前，把它从所有旧依赖集合里删掉。
否则三元分支 `state.ok ? a : b` 从 true 切到 false 后，旧分支读过的 `a` 仍会触发它 —— 幽灵依赖。
（`tests/reactivity.test.js` 的"分支切换后旧依赖被清理"专门验证这一点。）

**③ stop()**。把 effect 从账本上全部摘掉并标记 `active = false`。
组件卸载时必须停掉渲染 effect，否则数据一变它还试图更新已不存在的 DOM —— 最典型的内存泄漏。

## 三、账本（dep.js）

```js
targetMap: WeakMap<原始对象, Map<属性名, Set<ReactiveEffect>>>
```

- 第一层用 WeakMap：对象没有引用时整条账目自动回收。
- track：`activeEffect` 存在时（即"正在某个 effect 里读"）才记录，同时把 dep 反向记到
  `effect.deps` 上（清理时要用）。
- trigger 的分类学（`TriggerType`）：

| 操作 | 类型 | 额外要通知谁 |
|---|---|---|
| `obj.a = 1`（已有） | SET | `a` 的依赖 |
| `obj.b = 1`（新增） | ADD | `b` + **ITERATE_KEY**（for...in 结果变了） |
| `delete obj.b` | DELETE | 同上 |
| `arr[3] = x`（越界） | ADD | 下标 + **length**（虽然没显式写 length，它客观变了） |
| `arr.length = 1` | SET | `length` + 所有**下标 ≥ 新长度**的依赖 |

无限递归防护：effect 执行中触发了自己（读了又写同一个属性）→ 忽略；
调度器层面的重复触发则由 1000 次的循环守卫兜底并明确报错。

## 四、Proxy 拦截（reactive.js）

拦截的不只是 get/set，一共有五个 trap 各司其职：

| trap | 触发时机 | 为什么要管 |
|---|---|---|
| get | 读属性 | track；惰性深层代理 |
| set | 写属性 | 判断 SET/ADD，值没变（Object.is）不触发 |
| has | `'a' in obj` | in 的结果也要响应式 |
| deleteProperty | `delete obj.a` | 通知 ITERATE_KEY |
| ownKeys | `for...in` / Object.keys | 收集 ITERATE_KEY |

几个容易被问到的点：

**为什么必须传 receiver 给 Reflect？**
继承 + 访问器属性的场景：`const child = Object.create(reactiveParent)`，
读 `child.x` 时 getter 内部的 `this` 应该是 child（receiver），而不是 parent。
不传 receiver，依赖会被错误地记在 parent 上。

**惰性深层代理**：`reactive(大对象)` 不会递归遍历，只有真正读到某个嵌套对象时
才返回它的代理（每次 get 时 `reactive(res)`）。初始化 O(1)，这是相对
Vue 2 defineProperty 递归劫持的重大性能优势。

**同一个对象必须返回同一个代理**（reactiveMap 缓存）：
否则 `{ a: reactive(obj), b: reactive(obj) }` 里两个引用不相等，
依赖被记成两份，比较也会失效。

**数组的两个特殊问题（instrumentations）**：

1. `push` 内部会"读 length 再写 length"—— 同一个 effect 里读写自己 → 无限递归。
   解法：执行 push/pop/shift/unshift/splice 期间暂停依赖收集（pauseTracking）。
2. `reactiveArr.includes(原始对象)` 会返回 false（Proxy 的 !== 原始对象）。
   解法：includes/indexOf/lastIndexOf 先逐下标收集依赖，找不到时用原始值兜底再找一次。

## 五、ref 与 proxyRefs（ref.js）

Proxy 只能代理对象，`let count = 0` 没救。ref 的思路是**包一层对象**：
`ref(0)` → `{ value: 0 }`，value 的存取器里做 track/trigger —— 和 reactive 完全同一套账本。

```js
class RefImpl {
  get value() { trackEffects(this.dep); return this._value }
  set value(v) {
    if (hasChanged(v, this._rawValue)) {   // ★ 比较 _rawValue 而不是 _value
      this._rawValue = v
      this._value = toReactive(v)          // 对象值做深层代理
      triggerEffects(this.dep)
    }
  }
}
```

- 为什么比较 `_rawValue`？`ref(原始对象)` 的 `_value` 是 Proxy，
  再赋同一个原始对象时 `Proxy !== raw` 会误判"变了" → 多余的重渲染。
- **proxyRefs**：`setup` 返回 `{ count: ref(0) }`，模板里却写 `{{ count }}` 而不是
  `{{ count.value }}` —— 就是这个 Proxy 在读时解包、写时写回 `ref.value`。
  JS 里必须写 `.value`、模板里不用，这个"不一致"的根源就在这里。
- `toRef / toRefs`：不存值的"转发器"，读写都落到原对象的 Proxy 上，
  所以解构出来的 ref 和原对象天然双向联动。

## 六、computed：缓存 + 惰性（computed.js）

computed 内部也是一个 effect，区别在于它的 scheduler **不重算，只作废缓存**：

```
getter 依赖的数据变化
  → computed 的调度器被调用：dirty = true，并通知所有"读过 computed 的 effect"
  → 注意：此刻 getter 并没有执行！

有人读 computed.value
  → dirty 为 true → 执行 getter 重算 → 缓存新值 → dirty = false
  → dirty 为 false → 直接返回缓存（一次都不多算）
```

这同时做到两件事：**缓存**（依赖没变不重算）和**惰性**（变了也不立刻算，等真有人读）。
依赖链 `computed(computed(state))` 能正确传递，靠的是"读 value 时当前 effect 是 getter 的
effect，getter 里读到的数据依赖就记在 computed 头上，而不是记在下游"。

## 七、调度器：把 N 次修改合并成 1 次执行（scheduler.js）

没有调度器：`state.a=1; state.b=2; state.c=3` → 三次同步重渲染，两倍多的无效工作。
有了调度器：组件渲染 effect 的变化只做一件事 —— **job 进队列**，微任务里统一 flush：

```js
queueJob(job)      // Set 去重：同一 job 只入队一次；二分插入保持 id 升序
queueFlush()       // Promise.resolve().then(flushJobs) —— 推迟到微任务
flushJobs()        // 按 id 升序执行：父组件先于子组件更新
```

三个设计点：

1. **去重**：同一 tick 内改三次状态，组件只重渲染一次（demo 里"一次加 3"按钮可验证）。
2. **排序（id 升序）**：组件实例的 uid 单调递增，父的 uid 一定小于子。
   先更新父 → 父把新 props 传给子 → 子带着新 props 只更新一次。反过来的话子会更新两遍。
3. **执行期间允许插队**：flush 中父组件的更新可能让子组件的 job 入队，
   for 循环以 `queue.length` 为界自然吃掉新任务；无限递归有 1000 次守卫。

**nextTick** 就是 `currentFlushPromise.then(fn)` —— DOM 更新发生在 flushJobs 这个微任务里，
再排一个微任务自然就在它后面。这就是"改完数据立刻读 DOM 读到旧值、await nextTick 后才是新值"的原因。

## 八、把链路串起来

```js
const state = reactive({ count: 0 })

effect(() => {                     // ① 创建 effect 并立即执行
  document.body.textContent = state.count   // ② 读 count → track(state, 'count')
})

state.count++                      // ③ set 拦截 → trigger
// ④ 翻账本找到 ① 的 effect → 没有 scheduler → 立即 run() → DOM 更新
```

组件化之后，①的函数就是"组件的渲染函数"，③的通知会经过调度器排队 ——
再往后的事，就是[渲染器](./03-渲染器与Diff.md)和[组件系统](./04-组件化原理.md)的故事了。
