# 04 · 组件化原理：组件只是「type 为对象的 vnode」

> 对应源码：`src/runtime-core/component.js`（实例/setup/props/emit/渲染 effect）、
> `h.js`（withCtx/renderSlot）、`lifecycle.js`、`instance.js`。
> 可视化演示：`examples/components.html`（一个跑在 mini 框架上的 Todo 应用 + 生命周期日志）。
> 参考书目：《Vue.js 设计与实现》第 12 章（组件核心）、第 13～15 章。

这一篇是给"后续要深入组件化"做的铺垫。核心结论只有一句：

> **组件没有任何魔法。它也是一个 vnode，只不过 type 是对象而不是字符串；
> 渲染器看到对象就分派到组件流程；组件流程内部又回到"执行 render → 得到子树 vnode → patch"。**

## 一、渲染器眼中的组件

```js
createVNode('div', ...)   // type 是字符串 → processElement
createVNode(MyComp, ...)  // type 是对象   → processComponent
```

patch 里的一次分派，复杂度就被"封"进了组件流程 —— 元素流程对此完全无感。
模板里的标签名变成组件对象，靠的是编译器插的 `_resolveComponent("MyComp")`：
从 **setup 返回值 → components 选项 → 祖先链 → app.component 全局注册表** 逐级查找，
就近覆盖。

## 二、从 vnode 到 DOM：组件的一生

```
mountComponent(vnode)
  ① createComponentInstance     创建实例（组件"有状态"的载体）
  ② setupComponent              initProps → initSlots → 执行 setup()
  ③ setupRenderEffect           渲染函数包成 effect（带调度器），立即执行一次
       render() → 子树 vnode
       patch(null, 子树, container)   ← 又回到渲染器的元素流程！
  ④ 子树 DOM 冒泡               vnode.el = subTree.el
```

两个最值得咀嚼的点：

**① 组件 vnode 自己不产生 DOM，它的 DOM 来自子树。**
把 `subTree.el` 冒泡给组件 vnode 之后，对父组件的 diff 来说，
一个组件就"等同于"一个起始 DOM 节点 —— 内部嵌套多少层完全被隐藏。
这就是封装性在渲染层的体现。

**② 组件的更新 = 新旧子树的 patch**。父组件传来的 props 变了，或者组件自身状态变了，
执行的都是同一件事：重新 render 得到新子树，`patch(旧子树, 新子树)`。
和元素更新共用同一套 diff，没有第二套机制。

## 三、instance：组件为什么需要"实例"

元素是无状态的（同样的输入永远同样的输出），组件是有状态的：
setup 里的响应式数据、生命周期钩子、与父组件的连接、插槽……必须有个容器跨渲染周期存活。

```js
{
  uid, vnode, parent, appContext,
  subTree: null,      // ★ 组件渲染出的子树 —— DOM 的真正来源
  effect, update,     // 渲染 effect 与手动触发函数
  setupState,         // setup 返回值（proxyRefs 包过：模板里不用写 .value）
  props, attrs, slots,// 与外界的三个接口
  bm/m/bu/u/bum/um,   // 六组生命周期钩子数组
  provides,           // 原型链，见第七节
  isMounted, isUnmounted,
}
```

**instance.proxy** 是模板里的 `_ctx`（也是选项式 API 的 `this`）。
它是一个 Proxy，get 按 `setupState → props → data → ctx → $内置API` 的优先级查找。
模板里 `{{ msg }}` 能找到 setup 返回的 msg，就是因为编译器把它写成 `_ctx.msg`，
而 proxy 替你把这些来源抹平了 —— "数据来源透明"。
（反过来这也解释了经典报错：访问一个哪儿都没有的属性时会得到警告。）

`uid` 的唯一用途：调度器按它排序，保证**父组件先于子组件更新**
（父先更新才能把新 props 传下去，子只更新一次）。

## 四、props / attrs：下行数据的落地

`initProps` 把 vnode.props 分成两堆：

- 组件用 `props` 选项**声明过的**（kebab-case 自动转驼峰）→ `instance.props`，用 **shallowReactive** 包装。
- 没声明过的 → `instance.attrs`，并**透传**到组件根元素上（`renderComponentRoot` 里合并：
  class/style 做拼接合并，其余同名时根节点优先）。`<Child data-id="7">` 的 data-id 出现在
  Child 根 DOM 上，就是这条"属性继承"链路。

为什么 props 用浅响应式？props 的**替换**（父组件传了新对象）要触发子组件重渲染 ——
这一层要响应式；而 props 内部对象的深层变化应该由"数据本身的响应式"负责，不该让
props 系统再递归代理一遍（避免双重代理，也符合"props 是只读的"这个约定 ——
直接改 props 会被 proxy 明确警告）。

**props 更新的落地方式**（updateComponentPreRender）：父组件重渲染产生新的组件 vnode，
`shouldUpdateComponent` 对比新旧 props/插槽 —— 没变就**整个跳过**子组件的渲染
（这是父组件状态变化但与子组件无关时的关键优化）；变了就把新 vnode 记到 `instance.next`，
等渲染 effect 执行时先同步进 instance，再渲染。

## 五、emit：上行通信 = "事件就是特殊名字的 prop"

```js
emit(instance, 'add', text)
  // 在 vnode.props 里找 onAdd（'add' → toHandlerKey → 'onAdd'）
  // 找到就调用 add(text)
```

- 模板里 `@add="addTodo"` 编译产物是 `onAdd: _ctx.addTodo` —— 事件监听器就是一个 prop。
- `emit('update:modelValue', v)` 找 `onUpdate:modelValue` —— 这就是 **v-model 的全部机制**：
  编译器把 `v-model="x"` 展开成 `:modelValue="x"` + `@update:modelValue="x = $event"`，
  子组件 emit 一下、父组件的赋值表达式改一下自己的状态，双向绑定就完成了。
  名字可以换：`v-model:title` → `title` + `onUpdate:title`。
- 没有监听者不算错误（父组件可以不监听），只警告。

所以组件通信模型只有两条线：**props 下行、emit 上行**。双向绑定、事件总线式的模式，
全部是这两条线的组合或语法糖。

## 六、slots：插槽是"返回 vnode 的函数"，不是 vnode

```html
<!-- 父组件 -->
<Child><p>{{ parentMsg }}</p></Child>
```

编译产物：

```js
createVNode(Child, null, {
  default: _withCtx(() => [createVNode('p', null, _toDisplayString(_ctx.parentMsg), 1)]),
})
```

**为什么是函数而不是直接给 vnode？** 两个原因：

1. **惰性**：子组件没渲染 `<slot>`，这段 vnode 就永远不创建（省性能）。
2. **作用域与响应式归属**：函数体在**子组件渲染期间**被调用（renderSlot 里），
   函数里的 `_ctx.parentMsg` 通过闭包指向**父组件**的 ctx；
   `withCtx` 则在调用时把"当前渲染实例"临时切回父组件 ——
   插槽内容里写的 `<MyIcon>` 会在父组件的注册表里解析。
   于是"父组件的数据变化 → 插槽内容更新"这条链路成立：parentMsg 变化触发父重渲染 →
   新的插槽函数随新 vnode 流向子组件 → 子组件 patch 时重新调用它 → 内容更新。

**作用域插槽**是这个模型的自然延伸：`<slot :todo="todo">` 编译成
`renderSlot($slots, 'default', { todo: _ctx.todo })`，子组件把自己的数据当**参数**
传进父组件的函数 —— "作用域"二字的含义就是"这个函数的形参由子组件填充"。

`<slot>` 的编译产物 `renderSlot` 返回一个**带 STABLE_FRAGMENT 标记的 Fragment** ——
这不能是裸数组：插槽内容是运行期才确定的，只有打上 patchFlag 才会被收进父元素的块，
插槽更新才能传导到 DOM。（本项目第一版返回裸数组，插槽永远不更新 —— 测试抓出来的。）

## 七、provide / inject：跨层级通信 = 一条原型链

```js
// 子实例创建时
instance.provides = parent.provides ? Object.create(parent.provides) : Object.create(null)
```

provide 往自己的 provides 上写，inject 沿原型链向上找：
"自己 provide 的覆盖祖先的"（就近覆盖）是原型链**免费**送的语言特性，
一行 `key in provides` 就完成了查找。中间层组件完全无感知 ——
这就是它解决"props 逐层透传（prop drilling）"的方式。

## 八、生命周期：钩子为什么能"直接调用"

```js
// lifecycle.js
export function onMounted(hook) { injectHook('m', hook) }
// injectHook：把 hook push 进 currentInstance.m
```

- `onMounted` 能不传实例直接用，靠的是 **setup 执行期间的全局上下文**：
  `setupComponent` 用 `setCurrentInstance(instance)` 包住 setup 的执行，
  结束时恢复。所以生命周期 API **必须在 setup 里同步调用** ——
  放进 setTimeout 里 currentInstance 已经是 null，会得到警告。
- 用数组存钩子：同一种钩子可以注册多个，按注册顺序执行。
- 触发时机全部在 `setupRenderEffect` 的两条渲染路径里：
  挂载：bm → patch 子树 → （子组件的 m 先触发）→ m
  更新：同步 next(props/slots) → bu → patch → u
  卸载：bum → 卸载子树 + stop effect → **onUnmounted 进队列**，整棵树卸载完后按
  父先子后（FIFO）统一触发 —— 和真实 Vue 的 post 队列语义一致。

## 九、函数式组件与 defineComponent

- `defineComponent` 在运行时是**恒等函数**（原样返回）。它的价值全在 TypeScript：
  让类型系统理解 setup 返回值和模板、props 的对应关系。
- setup 直接返回函数 = 手写 render（函数式组件）。没有实例负担，适合纯展示组件。
