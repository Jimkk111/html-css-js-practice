# 02 · 模板编译：字符串是怎么一步步变成渲染函数的

> 对应源码：`src/compiler-core/`。可视化演示：`examples/compile-pipeline.html`。
> 参考书目：《Vue.js 设计与实现》第 12～15 章（编译器）、第 16 章（编译优化）。

整个编译器就是一条流水线，每一站只做一件事：

```
template 字符串
   │ ① tokenize        词法分析（有限状态机）
   ▼
token 流
   │ ② parse           语法分析（栈）
   ▼
模板 AST              —— 描述"模板长什么样"
   │ ③ transform        语义转换 + 优化标注 + 标识符改写
   ▼
JS AST + 优化信息      —— 描述"要生成什么代码"
   │ ④ generate         打印
   ▼
JS 源码字符串
   │ ⑤ new Function     变成可执行的 render 函数
   ▼
render(_ctx, _cache) => VNode
```

为什么拆成四站而不是直接字符串替换？因为每一站的信息密度不同：
token 是"字符片段"，AST 是"结构"，JS AST 是"语义"。拆开之后每一步都能被
单独测试、单独优化（Vue 的静态提升、块树都是在 transform 一站加进去的，parse 完全不用改）。

---

## 一、词法分析（tokenize.js）：有限状态机

**问题**：逐个字符扫描时，同一个字符在不同位置含义完全不同：

| 字符 | 在文本里 | 在标签里 | 在属性值里 |
|---|---|---|---|
| `>` | 普通字符 | 标签结束 | 普通字符 |
| `<` | 可能是标签开头 | —— | 普通字符 |
| `{{` | 插值开始 | —— | 两个花括号 |

**解法**：用"当前状态"决定怎么解释字符。这就是有限状态机（FSM）的全部思想。

本项目定义了 12 个状态（`tokenize.js` 顶部的 `State`），核心转移路径：

```
Text ──'<'──► BeforeTagName ──字母──► InTagName ──空白──► BeforeAttrName
                │ '!'                     │ '>'                │ '='
                ▼                         ▼                    ▼
             注释/Bogus                吐出 OPEN_TAG       InAttrValue(Quoted|Unquoted)
```

实现要点（对照源码看）：

1. **每个状态一个 case 分支**，读一个字符、要么消费进缓冲区、要么转移状态。
   整个扫描是 O(n) 单遍。
2. **缓冲区**（`textBuf`、`attrNameBuf`……）负责把"跨多个字符"的片段攒起来，
   在状态跳出的那一刻一次性吐出 token。
3. **容错**：`a < b` 这种文本里的 `<` 不能当标签（只认 `<字母` / `</` / `<!`）；
   结束标签多余、开始标签没闭合都只警告不崩溃。
4. 属性名允许 `: @ # . [ ] $ -` 这些"非 HTML 标准"字符 —— 因为 Vue 的指令
   `v-bind:x.sync`、`@click.stop`、`#header`、`:[dynamic]` 都依赖它们。

产出的 token 就五类：`OPEN_TAG`（带属性表）、`CLOSE_TAG`、`TEXT`、`INTERPOLATION`、`COMMENT`。

## 二、语法分析（parse.js）：用栈恢复嵌套

token 是扁平的，但模板的意义在于**嵌套**。恢复结构靠一个栈：

```
遇到 OPEN_TAG   → 建元素节点，挂到栈顶元素的 children，然后压栈
遇到 CLOSE_TAG  → 从栈里弹出，一路弹到名字匹配的那个（顺带容错"忘写闭合"的情况）
遇到 TEXT/插值  → 挂到栈顶元素的 children
```

这一站同时做了一个**决定编译器后半段命运的分类**：把属性分成两种节点

| 模板写法 | AST 节点 | 值 |
|---|---|---|
| `id="a"` | `ATTRIBUTE` | 字符串，**编译期定死** |
| `:id="x"` / `v-bind:id="x"` | `DIRECTIVE(name:'bind')` | JS 表达式，**运行时求值** |
| `@click="fn"` / `v-on:click.stop` | `DIRECTIVE(name:'on')` | 表达式 + 修饰符 |
| `v-if / v-for / v-model ...` | `DIRECTIVE(name:'if'...)` | 结构性指令 |

```js
// 指令节点的结构
{ type: 'Directive', name: 'on', arg: 'click', exp: 'fn', modifiers: ['stop'] }
```

**为什么这个分类是优化的地基？** 静态属性在编译期就是常量 → 可以静态提升、可以跳过更新对比；
指令是运行时行为 → 需要 patchFlag 提示运行时"这里会变"。后面所有优化都从这条分界线推导。

最后 `markElementTypes` 给每个标签打上第四种分类：**原生元素 / 组件 / slot / template**。
`<div>` 在 HTML 标签表里 → 元素；`<MyComp>` 不在 → 组件。这是"组件化"在编译器的第一个落点。

## 三、转换（transform.js）：信息量最大的一站

transform 要同时做三类事，按模板从上到下过一遍：

### 3.1 语义转换：模板语法 → JS 语法

| 模板 | 产物（简化） |
|---|---|
| `{{ msg }}` | `_toDisplayString(_ctx.msg)` |
| `@click="fn"` | `onClick: _ctx.fn` |
| `@click.stop="fn"` | `onClick: _withModifiers(_ctx.fn, ["stop"])` |
| `v-if / v-else-if / v-else` | 嵌套三元表达式，每个分支独立开块 |
| `v-for="(item,i) in list"` | `_renderList(_ctx.list, (item, i) => …)` 包在 Fragment 里 |
| `v-model="msg"`（input） | `value: _ctx.msg` + `onInput: $event => (_ctx.msg = $event.target.value)` |
| `v-model="msg"`（组件） | `modelValue: _ctx.msg` + `onUpdate:modelValue` —— **v-model 只是编译期约定** |
| `<slot name="a" :x="x">默认</slot>` | `_renderSlot(_ctx.$slots, "a", { x: _ctx.x }, () => […])` |
| `<template #tag="{ todo }">…</template>` | 插槽对象里的 `tag: _withCtx(({ todo }) => […])` |

两个有代表性的细节：

**v-model 的"降级"实现**：transformModel 把 v-model 直接拆成两个普通指令塞回 props，
后面的代码完全不知道 v-model 存在过。把特殊语法尽早降解成基本语法，
是编译器设计最常用的手法。

**v-if 的右结合三元**：`cond1 ? A : cond2 ? B : C` 恰好和 if/else-if/else 语义一致，
所以从最后一个分支往前构建即可。每个分支必须包成 `(_openBlock(), _createElementBlock(...))`
—— 原因见下文"块"。

### 3.2 标识符改写（expression.js）

模板里的 `msg` 在 render 函数里必须是 `_ctx.msg`（组件实例代理），否则是未定义变量。
`prefixIdentifiers` 做一次轻量词法扫描，给标识符加前缀，但**不能加**的更多：

| 输入 | 输出 | 为什么 |
|---|---|---|
| `msg + count` | `_ctx.msg + _ctx.count` | 普通标识符 |
| `a.b` | `_ctx.a.b` | `b` 是属性名 |
| `{ x: 1, y: a }` | `{ x: 1, y: _ctx.a }` | `x` 是对象键 |
| `'hello'` | 原样 | 字符串内容 |
| `Math.max(1,2)` | 原样 | 全局对象白名单 |
| `item => item.name` | 原样 | 箭头函数参数是局部变量 |
| `v-for` 的 `item` / 插槽解构的 `todo` | 原样 | transform 提前把它们塞进了作用域集合 |
| `_ctx.msg`（已处理过） | 原样 | `_` 开头不加前缀 → **幂等**，可安全重复处理 |
| `$emit(...)` | `_ctx.$emit(...)` | `$emit` 是实例属性；只有 `$event` 保持裸写 |

真实 Vue 用 babel 拿到完整 JS AST 来判断；本项目用保守的正则 + 白名单近似，
正确覆盖模板中 99% 的写法，且保留了"幂等"这个关键性质。

### 3.3 优化标注（Vue 3 快的根源）

**(1) patchFlag —— "这个节点哪里会变"**

| 场景 | flag | 运行时的收益 |
|---|---|---|
| `<p class="static">{{ msg }}</p>` | `1 TEXT` | 更新时直接改 textContent，属性、子节点全都不看 |
| `<div :id="x">` | `8 PROPS` + `["id"]` | 只对比 id 一个属性，O(动态属性数) |
| `:class` / `:style` | `2 CLASS` / `4 STYLE` | 归一化成本高，单独标记单独处理 |
| `v-bind="obj"` | `16 FULL_PROPS` | 属性集合本身动态，只好全量对比 |
| `v-for` 有/无 `:key` | `128 KEYED` / `256 UNKEYED` | 决定运行时走哪种 diff |
| 静态提升的节点 | `-1 HOISTED` | 更新时整棵跳过 |

对照 runtime-core 的 `shared/patchFlags.js`：数字和真实 Vue 完全一致，
你在浏览器 devtools 里看 Vue 编译产物时的 `1 /* TEXT */` 就是它们。

**(2) 静态提升（hoisting）**

```html
<div><p class="title">静态标题</p><span>{{ msg }}</span></div>
```

`<p>` 整棵子树没有任何动态内容 → 编译成模块级常量：

```js
const _hoisted_1 = _createElementVNode("p", { class: "title" }, "静态标题", -1)
function render(_ctx) {
  return (_openBlock(), _createElementBlock("div", null,
    [_hoisted_1, /* 动态 span */]))
}
```

每次重渲染不再重新创建 `<p>` 的 vnode（省 GC），更新时也完全不碰它（flag 为 -1 不会被收进块）。

安全边界（初学者自己写编译器最容易踩的坑）：
- **v-for 里绝对不能提升** —— 提升的 vnode 是共享常量，上面挂着 `el`（真实 DOM 引用），
  所有迭代项共享一个 el，diff 会彻底错乱。
- 共享 vnode 被"使用"时会被浅拷贝（`cloneIfMounted`），每个位置有自己的 el。

**(3) 块（Block）与 dynamicChildren**

即使有 patchFlag，更新还是要递归整棵树才能找到动态节点。块的思路是：
在**可能含动态后代**的地方（模板根、v-if 分支、v-for 的迭代项）开一个"收集器"，
把所有动态后代**平铺**登记进来：

```js
// 运行时（vnode.js）
openBlock()               // 压栈一个空数组
_createElementBlock(...)  // 创建节点时：patchFlag>0 或是组件 → 登记进当前数组；最后数组挂到 dynamicChildren
```

```html
<div>                     ← 块
  <section>               ← 静态，不收集
    <p>hello</p>          ← 静态，不收集
    <span>{{ msg }}</span> ← 动态，收集 ✓
```

`div.dynamicChildren = [span]`。更新时渲染器只看这个数组 ——
十层嵌套里只有一个动态节点，更新成本就是 O(1)，**与树的深度无关**。

为什么 v-if / v-for 必须各自开块？因为分支切换、迭代次数会让"动态节点数量"变化，
如果和外面共用一个块，新旧 dynamicChildren 就对不上号，按位置 diff 会错位。
真实 Vue 连 `createCommentVNode('v-if', true)`（假分支占位）都要作为块登记，就是为了让
"切分支"前后的结构保持可对比。

**(4) 文本合并（transformText）**

```html
<li>{{ index }} - {{ item.name }}</li>
```

直觉上 children 是 3 段。但插值不是 vnode，收不进块，也打不了 TEXT 标记 → **永远不更新**。
真实 Vue 的做法：把连续的"文本+插值"合并成一个表达式
`_toDisplayString(index) + " - " + _toDisplayString(item.name)`，
它变成一个动态文本子节点 → TEXT 标记 → 更新时一次 setText。
这个优化同时也是**正确性**的需要，本项目第一版就栽在这里。

### 3.4 同类坑再记一笔（本项目真实踩过、测试覆盖的）

| 坑 | 症状 | 修复 |
|---|---|---|
| 静态 class 和 :class 各生成一份 | 对象里两个 class 键，静态类丢失 | 合并成 `normalizeClass(["todo", { done: x }])` |
| `@change="$emit(...)"` 被当函数引用 | 渲染时立即调用 emit，事件绑不上 | 只有裸标识符/成员链才不包箭头函数 |
| `onUpdate:modelValue` 当裸键 | 产物语法错误（冒号） | 打印器对非法标识符键加引号 |
| `$emit` 不加 `_ctx.` 前缀 | 运行时 ReferenceError | `$` 开头也要前缀（只有 `$event` 裸写） |
| 无 props 的 vnode key 为 undefined | 与 key=null 的节点判为"不同"，DOM 全部重建 | `key: props?.key ?? null` |
| `<slot>` 返回裸数组 | 插槽内容收不进块，永远不更新 | renderSlot 返回带 STABLE_FRAGMENT 的 Fragment |

## 四、代码生成（codegen.js + js-ast.js）

transform 挂在 AST 上的 `codegenNode` 是一棵 **JS AST**，codegen 只负责打印。
先建 AST 再打印（而不是直接拼字符串）的好处：括号、逗号、键名引号这些规则
集中在一个打印器里处理，不会散落在拼接代码的每个角落。

打印器里值得看的三条规则：

```js
// ① 对象键不是合法标识符时必须加引号
"onUpdate:modelValue"      // v-model 组件事件的产物
// ② 嵌套表达式按优先级加括号（js-ast.js 的 precedenceOf）
(a || b) && c              // 子节点优先级低 → 加括号
// ③ 数组/对象超长时换行缩进，产物可读
```

最终 `generate()` 组装出三段：

```js
const _Vue = Vue                                  // ← new Function('Vue', ...) 传进来的运行时
const { toDisplayString: _toDisplayString,        // ① helper 解构：只有用到的才出现
        createElementBlock: _createElementBlock } = _Vue

const _hoisted_1 = _createElementVNode(...)       // ② 静态提升

__exports.render = function render(_ctx, _cache) { // ③ 函数本体
  return (...)
}
```

`compile()` 最后一步 `new Function('Vue', '__exports', code)` 把字符串变成函数，
传入的 `Vue` 就是 `RUNTIME_HELPERS` 表 —— **编译器生成的每个 `_xxx` 都必须在这张表里有实现**。
这就是"编译器版本和运行时版本必须严格配套"的技术原因。

## 五、运行时编译 vs 构建时编译

同一套编译器，两种用法：

- **运行时编译**（本项目）：`src/index.js` 把 compile 注入运行时（`setRuntimeCompiler`），
  组件写 `template` 就现场编译。代价：浏览器里多干一份编译的活，产物体积大。
- **构建时编译**（真实 Vue 的 SFC）：vite-plugin-vue 在打包阶段就编译好，
  产物里只有 render 函数，运行时根本不需要带编译器 —— 这就是
  `vue.runtime.esm-browser.js` 比完整版小一半的原因。

两者共用同一套 parse/transform/generate。理解了本项目，你就理解了 SFC 编译器的核心；
SFC 额外做的只是：解析 `<script>`/`<style>`、处理 scoped CSS、生成 source map。
