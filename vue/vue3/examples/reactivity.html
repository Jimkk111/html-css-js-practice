响应式系统：数据变化时，为什么函数会自动重新执行？

答案只有一句话：读取时记录"谁读了我"（track），写入时通知"读过的人"重新执行（trigger）。 Proxy 是拦截读写的手段，effect 是"被通知的人"。下面把这条链路完全摊开给你看。

实验一：批量更新（调度器）

组件的渲染函数是一个 effect，但它不直接重跑—— 数据变化只把它放进队列，本微任务结束时统一执行一次。试着连点三下：

count = 0

渲染次数：0

「一次加 3」点了之后渲染次数只 +1 —— 这就是 Vue "异步批量更新"的直观收益。

实验二：computed 的缓存与惰性

computed 也是 effect，但它被通知时只把缓存标记为过期（dirty）， 等真的有人来读 .value 才重算。

sum = 10

getter 实际执行次数：0

改数字后先别点按钮——你会发现执行次数不变（惰性）；点了才 +1（读到才重算）。

trigger 日志：看一眼"账本"怎么流动

（操作上面的控件，这里会打印 track/trigger 的细节）

原理一页纸

const state = reactive({ count: 0 })

effect(() => render(state.count))     // ← 组件的渲染函数就是这么"活"起来的
//   └─ 执行时读到 state.count → Proxy get 拦截 → track(state, "count")
//      账本记下：targetMap[ state ]["count"] → [渲染effect]

state.count++                          // ← 写入
//   └─ Proxy set 拦截 → trigger(state, "count")
//      翻账本找到依赖它的 effect → 有 scheduler 就交给调度器（排队，微任务里批量执行）
//      没有就立刻 effect.run() 重新执行

ref 呢？  原始值没法被 Proxy 拦截，于是包一层对象 { value: 0 }，
         读写 .value 同样走 get/set → 复用同一套 track/trigger。

computed 呢？ 一个带 scheduler 的 effect + dirty 缓存标记：
         依赖变化 → 只把 dirty 置 true 并通知下游；被读取且 dirty 才重算。

数组呢？ push/pop 会读写 length：执行期间暂停收集（防自我触发）；
         includes 找不到时用原始值兜底再找一次（代理对象 ≠ 原始对象）。
