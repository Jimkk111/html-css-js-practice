模板是怎么被编译成渲染函数的？

在下面写一段模板（左边有可点按的例子），右边会实时展示编译器四个阶段的产物。 核心结论：模板只是"给人看的写法"，编译之后它就变成一个普通 JS 函数， 函数执行时返回一棵虚拟 DOM 树 —— 之后的事都交给渲染器（下一个页面）。

试一试

阶段 1 词法分析 tokenize —— 字符流 → token 流

有限状态机逐字符扫描。同一字符在不同语境下含义不同（> 在文本里是普通字符，在标签里是结束），所以必须靠"状态"决定怎么处理。

#type内容

阶段 2 语法分析 parse —— token 流 → AST

用栈恢复嵌套关系；属性被分成静态 ATTRIBUTE（编译期定死）与指令 DIRECTIVE（运行时求值）。这个区分是所有优化的地基。

    阶段 3+4 transform 优化 + generate 生成 —— AST → render 函数源码

    transform 做了三件大事：①语义转换（v-if→三元、v-for→renderList、@click→onClick）； ②优化标注（patchFlag 告诉运行时"哪里会变"、静态子树提升到函数外只创建一次、开块收集动态后代）； ③标识符改写（msg → _ctx.msg）。 下面产物里 数字标注 就是 patchFlag，_hoisted_N 就是静态提升。

    三个值得盯着看的细节
    
      
      
        
    • 静态提升：没有动态绑定的子树被提到 render 函数外面，成为模块级常量，
          更新时连比较都不需要（去试试第一个例子，注意 _hoisted_1 和 patchFlag -1）。

          打上 TEXT 标记 —— 更新时一次 setText 完成，不用 diff。

    • key 的去向：v-for 里 :key 出现在 props 里，但不在 dynamicProps 清单里 ——
          因为 key 一变节点就会被重建，根本轮不到"属性更新"这一步。
